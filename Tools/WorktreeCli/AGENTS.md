# WorktreeCli

Standalone Windows console application for repository coordination. It owns serialized MSBuild invocation, landing leases, and the Git-backed `Documents/Plans` scheduler. It never connects to a game endpoint or owns the AgentHarness lock.

## Executable and Commands

Use `Tools\WorktreeCli\Platforms\VisualStudio2026\Output\WorktreeCli.exe` through the provisioned primary Output link. Routine linked-worktree workflows do not build or modify that output; wrapper session start incremental-rebuilds it in the primary so it tracks primary HEAD, and source changes use the `/compile` [candidate/promotion path](../../.agents/skills/compile/references/worker.md).

- `lock token|claim|status|refresh|recover|release|steal` operates on landing locks identified by `--repo`. Lease state, not a record of which process took the claim, determines whether a lock is still held. A lease is lock ownership with a time limit that expires on its own if it is not renewed or released. `refresh` renews only a live lease held by the supplied owner; after expiry, `recover` and bounded `claim` can transfer ownership only while no registered worktree has a Git operation in progress. `claim` accepts a bounded blocking wait through `--wait-seconds` and `--poll-milliseconds`. Lock responses report lease identity, timing, and validation state only, never private record fields such as the process id that took the claim, so no caller can start reading a process id as proof the lock is still alive. The stored record must still carry that process id in range to validate; a lease record missing it reads as unverifiable and fails closed. The shared store can hold other lock domains, but this surface stays repository-only: do not add a `--domain` option or harness-key support.
- `plan validate|list|claim-next|claim-status|unclaim|complete|reject` is the only scheduler surface. It reads tracked `Documents/Plans` metadata, uses deterministic newest-first `(createdUtc descending,path)` selection, and stores only short-lived machine-local claim records. `validate` lints metadata and reports excluded plans, stale dependency edges, and healed claims; it evaluates no baseline and compares no metadata across commits. `validate --lint-only` runs that lint alone: it takes no scheduler guard, creates no storage, and heals nothing, so it reports `healedClaims` as an empty array, and every other plan operation rejects the switch as a usage error. `list` previews the scheduler row states from the session tree without changing anything: it takes no scheduler guard, heals nothing, creates no storage, and reports every executable Plan of the session tree in the same newest-first order as `eligible`, `blocked` naming its unmet prerequisites, `excluded` with its diagnostic, or `claimed` with the live claim's session, worktree, and expiry; documents whose metadata never parsed stay in the diagnostics instead of becoming rows, and a claim record it cannot use is ignored rather than deleted. `list` requires session `HEAD` to be on the primary line — an ancestor of, equal to, or a descendant of the primary tip, the last being the shape a prepared landing candidate has — and reports `git-identity-mismatch` for a session related in neither direction. `claim-next` requires session `HEAD` to be an ancestor of (or equal to) the primary tip, evaluates eligibility, dependency blocking, and healing against the primary tip so a behind session never heals a peer's claim or claims past a prerequisite landed after its baseline, and reads the exact bytes the selector uses from the session tree. WorktreeCli alone compares a targeted request with an existing session claim: `claim-status --plan` and `claim-next --plan` return `claim-plan-mismatch` with the different normalized `requestedPlan` and `heldPlan` while leaving the claim unchanged. `complete` and `reject` rewrite the markers of direct dependency children, delete the target Plan file, and report every changed path; `reject` additionally requires `--user-authorized-rejection`.
- `build` prints one `broken-engine-build-result/v1` JSON object to stdout; human progress goes to stderr. It retains the combined MSBuild stream in the invoking worktree's ignored `Temp\AgentBuildLogs\` path and parses structured diagnostics from that same stream.
- Exit code `0` is success, `2` is a state conflict or negative result, and `1` is usage, transport, or OS failure. A build whose MSBuild step succeeded but whose retained log came out incomplete still exits `1`, with `retainedLog.complete` false, because the JSON result is only trustworthy when the log behind it is whole.

`BROKEN_ENGINE_MSBUILD_PATH` pins discovery and fails when invalid. `BROKEN_ENGINE_BUILD_LOCK_WAIT_SECONDS` may only shorten the standard 500-second lock wait and exists for fixtures.

## Coordination State

Landing locks and scheduler claims live under `%LOCALAPPDATA%\BrokenEngineLocks`. Scheduler claims are keyed by Git common directory and expire after 48 hours; invalid, expired, and orphaned local records self-heal. `Documents/Features` and `Documents/Investigations` are not scheduled.

Missing dependency paths are satisfied with a stale-edge notice. Invalid metadata and dependency cycles exclude only their affected Plans component from selection; unrelated valid plans remain claimable.

Executable markers contain exactly `createdUtc` and `dependsOn`; timestamps use canonical millisecond UTC (`yyyy-MM-ddTHH:mm:ss.fffZ`). Every tracked `Documents/Plans` document carries one at byte zero; an absent marker — including one displaced by a BOM — reports `invalid-metadata` naming the path. `AGENTS.md` and `CLAUDE.md` are exempt at any depth.

A claim records the Plan path, its owner, session, worktree, and branch, and its claim and expiry timestamps. It stores no baseline commit, digest, or lifecycle state, so a session that rebases or advances keeps the claim it holds. Healing deletes a record only when it is unreadable, schema-invalid, stored under the wrong claim filename, expired, bound to a worktree path that no longer resolves, or bound to a Plan that is absent or invalid at the primary tip — the last rule is what lets landing delete its own claim best-effort and heal a missed delete later.

Scheduler and claim paths require successful repository and Plan hash derivation; if either is unavailable, the command returns the existing `local-app-data-unavailable` error and never uses a fallback path. Healing remains per-record, so a later Plan-path hash failure can leave legitimate deletions already made for earlier records. With successful hashes, scheduler selection and claim handling use their documented paths.

Enumeration skips unreadable, schema-invalid, and expired claim records instead of failing on them; for claim-record read/validation, only a directory-scan error aborts the operation. Recovery removes only the diagnosed `.lock` file. Every scheduler change runs under the scheduler guard — a lock it must acquire first, so only one change touches scheduler state at a time — and waits up to 500 seconds for it: contention alone reports `busy` as a state conflict, while an unusable lock file or its storage reports `guard-unavailable` as an OS failure. Scheduler changes fail closed: final operations clean only the hidden ordinary files stored next to the Plan file and updated atomically, and only those matching the exact Plan-owned temporary filename shape. Before cleaning Plan-owned temporary files, staging or rewriting Plan files, or deleting the target Plan, they stop with a state conflict when an existing non-guidance child's dependency relation is unknown, when a known direct child carries invalid metadata, or when the target file exists untracked; known unrelated invalid Plans, guidance, and tracked missing files do not block. Never broadly delete coordination state.

## Project Ownership

Keep source membership synchronized between `WorktreeCli.vcxproj` and `.filters`. Shared Windows and coordination code belongs in `Tools/ToolCommon` and is compiled into both tools. Transient operation claims around shared-tool consumption use `.agents/scripts/WorktreeCliSessionExclusion.psm1`; bootstrap incremental-rebuilds the WorktreeCli, AgentHarness, and ThirdParty primary outputs at every session start, and best-effort prebuilds DataPacker Release so new worktrees seed it by verified copy. When that prebuild is stamped, bootstrap then runs it to re-export the primary game data, first waiting up to its `-WaitSeconds` budget for any `BrokenEngineSandbox*` process to exit and skipping the run with a warning only if one is still alive when that budget expires; the run itself is not best-effort, and a nonzero exit fails session start.
