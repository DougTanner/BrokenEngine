# Select runtime data mode

Every worktree game build uses one data mode and one authoritative directory for both client and server:

- Shared is the default for ordinary code changes. Its Data directory is the primary checkout's `Projects\BrokenEngineSandbox\Platforms\VisualStudio2026\Output\Data`; this mode consumes primary generated headers/packs and disables every DataPacker build/export step.
- Local is mandatory when tracked changes from the resolved baseline, staged changes, unstaged changes, or untracked files touch `DataPacker/**`, `Engine/Data/**`, `Projects/BrokenEngineSandbox/Data/**`, `Common/DataFile.h`, generated-header logic, exporter versions/fingerprints, compression, chunk layout, or pack/manifest contracts. Its Data directory is the same path under the worktree's own repository root.
- A user may force Local. Never force Shared over a Local trigger. Local never falls back to Shared data. Generate Local output only with explicit authorization; a user-approved plan or acceptance criterion requiring shader or data repack is authorization.
- An absent worktree `Data` output never blocks Local. A linked worktree that has never generated has no `Output\Data` directory at all; that is the legitimate expected starting state, not missing setup. On an authorized Local generation build DataPacker seeds it from the primary checkout itself — the Local generation section below states the exact mechanism and its conditions. Never stop, ask the user to pre-stage output, or hand-run an export because the directory is absent. The only thing an agent must supply is generation *authorization*; the genuine blockers are validation and environment failures DataPacker reports itself — an unrecognized reparse point, absent primary output, or insufficient disk — never a user-prepared directory.
- Deletion-only exception: pure deletions of source asset files under `Engine/Data/**` or `Projects/BrokenEngineSandbox/Data/**` do not trigger Local when a repository-wide search proves nothing tracked references the deleted asset's generated identity (its generated CRC constant, chunk, or path). Claim it with `-DataBuildMode Shared -AcceptDeletionOnlyException`; the build re-checks every trigger-matching changed path against `deletionOnlyCandidates` and blocks under one typed code when any of them is not a baseline deletion or lies outside those two asset prefixes, so the switch asserts your reference-search evidence and never substitutes for it. Without `RunDataPacker` the build consumes only pre-existing generated output, which a source deletion cannot alter — the dead chunk persists in the published pack and the unused constant in the generated header until the next real DataPacker export drops both. Record the reference-search evidence with the mode selection. Any addition, modification, rename, exporter, or contract change keeps the Local requirement.

The game projects detect the authoritative repository-root Git marker. A linked worktree has a `.git` file and defaults `RunDataPacker=false`; the primary checkout has a `.git` directory and preserves ordinary Local Visual Studio behavior by defaulting true. An explicit Local `RunDataPacker=true` permits deliberate worktree generation; Shared rejects true.

The resolved context's `changedPaths` is the changed-path set, and its `dataBuildMode` covers the four path triggers only (`dataBuildModeDerivation: path-rules-only`). The remaining triggers above stay your judgment: if a changed file may affect generated or serialized bytes and the path rules do not prove otherwise, select Local even when the script reports Shared.

The build invocation derives the mode, both directories, and the four `DataBuildMode`/`RunDataPacker`/`GameDataDirectory`/`GeneratedDataIncludeRoot` properties itself, for every client/server solution, project, and selective compile alike; no agent command composes them. Your mode judgment enters through two invocation forms:

- `-DataBuildMode Local` — force Local when a changed file may affect generated or serialized bytes and the path rules do not prove otherwise. The invocation then moves mode and both directories together, so they can never disagree.
- `-DataBuildMode Shared -AcceptDeletionOnlyException` — the deletion-only exception above, and the only way Shared may win over a Local path trigger.

`RunDataPacker=true` is set by `-RunDataPacker` alone, and only for the single authorized generation build; every other build is `false`. That generation build also needs `DevEnvDir` for the game project's nested DataPacker build: the invocation resolves it internally, and `dev-env-dir.unresolved` blocks the generation build. `DevEnvDir` is structurally confined to that one build, so it cannot leak into later ones.

Every selected Data directory must be an absolute ordinary non-reparse directory containing exactly the 23 generated files: `Data.h`, `DataTypes.h`, and one nonempty header, manifest, and pack for each of `Audio`, `Scene`, `Islands`, `Model`, `Shader`, `Texture`, and `Raw`. The build invocation enforces this by running the oracle scripts itself: it issues receipts through `scripts/New-DataOracleReceipt.ps1` under the ignored `Temp\CompileDataOracle` parent and verifies them through `scripts/Test-DataOracleReceipt.ps1` before and after every consuming build, requiring each script's exit `0` and typed `status:pass`, `code:ok` result. Missing, extra, empty, replaced, reparse, or changed entries fail closed. Never issue or verify a receipt by hand as a separate agent command; the harness handoff reads the identities the build reports.

Because a fresh shell keeps nothing in memory, the invocation persists exactly the non-derivable oracle state in the ignored `Temp\compile-oracle-state.json` (`broken-engine-compile-oracle-state/v1`): the selected mode, the selected and independent Shared receipt identities with their breach flags and aggregate content digests, whether the authorized Local generation completed, and a digest of every changed path the Local receipt was issued for. Everything else — root, primary checkout, baseline, changed paths, mode, directories, tool paths, `DevEnvDir` — is re-derived on every call. The state machine keeps the rules on this page unchanged:

- Shared with no persisted Shared identity issues a fresh Shared receipt; a persisted one is verified before the build. A Shared identity persisted by an earlier build of either mode counts as persisted here — Shared mode adopts a Local build's independent primary identity as its selected identity, and a Local build adopts a Shared build's selected identity as its independent primary check — so its drift or breach still clears only through the transition below.
- Local with no current entry and no `-RunDataPacker` is the typed block `local-data.missing`; the build never auto-generates.
- A persisted Local receipt whose recorded input digest no longer matches the freshly derived one is the typed block `local-data.stale`, so a stale Local identity can never be inherited across shells or tabs.
- A receipt a post-build verification failed is persisted as breached and fails closed before every later build. Only two transitions clear a breach: `-ReissueSharedReceipt` for the Shared receipt, and a newly authorized `-RunDataPacker` generation for the Local one.
- An unreadable or non-conforming state file is the typed block `oracle-state.invalid`, naming the file and its remedy; a simply absent file is the legitimate fresh state, from which Shared issues a receipt and Local still requires authorization.

The wrapper bootstrap refreshes Shared data on a best-effort basis: at session start it runs the primary's DataPacker over the primary checkout's current asset inputs, which are not checked against HEAD, and it skips the run when the DataPacker prebuild was not stamped. It first waits up to its `-WaitSeconds` budget for any `BrokenEngineSandbox*` process to exit, and skips the run with a warning only if one is still alive when that budget expires. A peer session starting mid-session can therefore move primary Data under this session, failing a Shared receipt issued before that start, and a regenerated header can force a recompile here.

Ordinary Shared work otherwise remains unchanged: primary Data, no `RunDataPacker`, and no materialization or export. A Local receipt and a Shared receipt are independent identities; never require their aggregate or entry digests to equal. Every Local build also issues and verifies a separate Shared receipt for primary Data before and after the game build, so a change to primary data fails closed.

Local mode may build the worktree Release DataPacker as a standalone compile check (`-Target DataPacker`). An authorized same-baseline Local generation is the single invocation `-RunDataPacker`, which internally invokes the worktree DataPacker exactly once with `--materialize-data` over `Engine\Data` and `Projects\BrokenEngineSandbox\Data` into the Local Data directory, requires exit `0`, then issues the pre-generation oracle receipt and runs the one `RunDataPacker=true` game build. Materialization performs no exports and never creates, inspects, or materializes Attribution. In a validated linked worktree, dirty output uses copy-on-write materialization, staging primary files and atomically replacing only the affected recognized link.

Agent-driven Local generation forbids Gaea by default: the invocation scopes `BT_DATAPACKER_FORBID_GAEA_EXPORT=1` around the whole generation build and restores the caller's prior environment exactly. `-AllowGaeaExport` omits that guard and is authorized only by an explicit user-approved plan or acceptance criterion that requires regenerating Gaea output; changed island inputs, DataPacker code, fingerprints, or cache state alone never authorize a Gaea run. If the guard blocks a dirty Gaea route, the generation build failed: report the exception and do not pass `-AllowGaeaExport` or retry without that explicit approval. `BT_DATAPACKER_FORBID_EXPENSIVE_EXPORT` retains its broader independent meaning; never clear either caller-provided guard.

After a successful generation build the invocation issues the new Local oracle receipt, records that the generation completed, and verifies it plus the independent primary Shared receipt. Every later build — the other target and everything after it — omits `-RunDataPacker` and reuses that persisted Local receipt exactly. Re-invoking the identical `-RunDataPacker` command after a host timeout is safe once the prior invocation's process has ended: when the generation already completed for the same inputs and the Local receipt is unbreached, the invocation downgrades itself to an ordinary Local build, states the downgrade in its summary, and does not regenerate. Producer or data changes may replace the pre-generation Local receipt only when the approved plan or acceptance criterion authorizes the resulting content delta; otherwise any digest change is a blocker. The explicit `-RunDataPacker` is that authorization, so the replacement never blocks, but the delta is never absorbed silently either: the invocation keeps the pre-generation aggregate digest and a changed flag beside the new receipt in the state file and reports both digests in its stderr summary, so an unexpected generated-data change stays visible.

Without generation authorization, a current Local receipt prepared after the relevant worktree changes is required and verified exactly. If it is absent or stale the invocation blocks with `local-data.missing` or `local-data.stale` — Local generation authorization is required — and does not build, export, materialize, or fall back.

The independent primary Shared receipt is verified after each Local game build too. A peer session start is a possible explanation for a failure, not proof of one — that refresh is often skipped and can change nothing — so confirm that a session-start refresh produced the change before re-running with `-ReissueSharedReceipt`, which is the only way to accept the drift and issue a new Shared receipt. Every unconfirmed primary write fails the workflow. Hand both receipt identities from the build's reported summary to the harness. Never copy worktree DataPacker/data source changes into the primary checkout to test them.
