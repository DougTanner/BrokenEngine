# Agent - Game Command Dispatch

## Overview

Game-owned command handlers expose simulation, scene, save/replay, and diagnostic operations through the engine agent transport (`../../../../Engine/Source/Agent/AGENTS.md`). Engine-owned shared commands dispatch first; the game dispatcher then handles game-owned both-endpoint commands, then — under `BT_CLIENT` — the engine's client-generic handler, before routing remaining commands to its side-specific handlers under `BT_CLIENT` or `BT_SERVER`. Focused game Commands modules own the both-endpoint collection-layout and registry fixtures and the server-only fault fixtures; top-level dispatchers only route these commands. The focused server simulation-fixture module owns the parsing, result assembly, and orchestration for `inject_status_changes`, `spawn_players`, `replay_record`, `replay_play`, `replay_transfer_capture`, `replay_drop_retained_end_frame`, `replay_inject_persistence_failure`, `replay_transfer_fixture`, and `inject_outward_transfer`.

## Contracts

- Treat JSON parameters as hostile external input. Validate required fields, types, ranges, and referenced state; throw to let the engine transport produce a failure response.
- The engine owns client capture, window state, UI/input automation, and the client `query_profile` query (`../../../../Engine/Source/Agent/AGENTS.md`). Game client handlers own scene queries, client network fixture schemas and scenario sequencing, the desync probe, and moving the client's own grid cell. Focused game Agent modules own deferred subscription response state, full-state stall state, and armed packet bytes; the engine Agent owns the subscription fixture's engine-side capture and hooks. The client Debug audio streaming handler owns that command's validation, result assembly, scenario sequencing, deferred state, and fixed game assets; the engine Agent owns its audio/File state and hooks. Cell moves require a connected session whose player is already assigned, because before assignment the client subscription policy falls back to origin and discards the requested cell.
- Server handlers own simulation controls, status-change injection, frame and CPU profile queries, and save/replay operations. Their focused simulation-fixture module owns one state slot bound to the live `ServerSession`, including the coordinate-keyed status and replay-transfer queues; replacing or destroying the bound session clears that state. Server `query_profile` may acknowledge one retained raw-profile event by its exact nonzero sequence; `inject_status_changes` may request the matching activation arm only as an exact `{arm:true}` object. The arm is accepted only in a normal unpaused 1/1 server with recording/replay inactive, and validated changes plus the arm commit as one main-thread transaction; an occupied or overrun event rejects the batch before queue mutation. Save/load `file` values are appdata-relative bare filenames: reject empties, embedded NUL, separators, `..`, `:`, and Windows reserved device basenames.
- A deliberately fatal client fixture cannot do its fatal work inside its handler, given the engine transport's handler-exception handling (`../../../../Engine/Source/Agent/AGENTS.md`): `client_packet_fault_fixture` only arms its packet and `Game::ProcessGameMenuInput` delivers it outside that transport catch. Move and clear both the bytes and bound session before delivery so an exception or replacement session cannot leave the fixture armed.
- Replay commands fail when `kbDebugInput` is disabled because the simulation will not consume those requests.
- Replay transfer fixtures are server-only debug controls, and their queue also seeds the arrivals of fixtures that run outside replay, so draining it stays independent of replay state. Keep their injected state deterministic; a Blaster fixture must materialize a newly live destination's derived terrain grid before selecting a terrain-clear position for both its spawn and first fixed-tick movement, since Blasters destroy themselves on terrain contact.
- The game Agent owns replay transfer type classification, capture-count storage shape, and command JSON fields. The [engine replay fixture](../../../../Engine/Source/Agent/AGENTS.md#architecture) owns how those counts are observed and when the classifier is invoked.
- Commands that wait for a later frame, for the queue where messages wait for the renderer to pick them up, or for an input script use the engine deferred-response path. Ensure every deferred operation can resolve or fail without blocking the single in-flight channel.
- Scene queries are client-only and read render-visible state. Server frame queries read deterministic simulation state and must preserve collection/type validation.
- The frame registry keeps no rows, so nothing about it is enumerable or countable through a query. Its state reaches the harness only as the handle columns the collections themselves own, and the both-endpoint `registry_fixture` proves its behavior over its own fixed local data rather than over a frame.
