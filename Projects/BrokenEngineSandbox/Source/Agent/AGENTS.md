# Agent - Game Command Dispatch

## Overview

Game-owned command handlers expose simulation, scene, save/replay, and diagnostic operations through the engine agent transport (`../../../../Engine/Source/Agent/AGENTS.md`). Engine-owned shared commands dispatch first; the game dispatcher then handles game-owned both-endpoint commands, then — under `BT_CLIENT` — the engine's client-generic handler, before routing remaining commands to its side-specific handlers under `BT_CLIENT` or `BT_SERVER`. Focused game Commands modules own the both-endpoint collection-layout and registry harness rigs and the server-only fault harness rigs; top-level dispatchers only route these commands. The focused server simulation-harness-rig module owns the parsing, result assembly, and orchestration for `inject_payload`, `replay_record`, `replay_play`, `replay_transfer_capture`, `replay_drop_retained_end_frame`, and `replay_inject_persistence_failure`; the focused server frame-edit module owns `edit_frame`.

## Contracts

- JSON parameters fall under the engine's agent-channel exemption (`../../../../Engine/Source/Agent/AGENTS.md` `## Architecture`).
- The engine owns client capture, window state, UI/input automation, and the client `query_profile` query (`../../../../Engine/Source/Agent/AGENTS.md`). Game client handlers own scene queries, client network harness rig schemas and scenario sequencing, the desync probe, and moving the client's own grid cell and its viewer pin state (`../../Documents/AgentHarness/commands-client.md`). Focused game Agent modules own deferred subscription response state, full-state stall state, and armed packet bytes; the engine Agent owns the subscription harness rig's engine-side capture and hooks. The client Debug audio streaming handler owns that command's validation, result assembly, scenario sequencing, deferred state, and fixed game assets; the engine Agent owns its audio/File state and hooks. Cell moves require a connected session whose player is already assigned, because before assignment the client subscription policy falls back to origin and discards the requested cell.
- Server handlers own simulation controls, status-change injection, frame and CPU profile queries, and save/replay operations. Their focused simulation-harness-rig module owns one state slot bound to the live `ServerSession`, including the coordinate-keyed status and transfer queues that `inject_payload` fills; replacing or destroying the bound session clears that state (`../../Documents/AgentHarness/commands-server.md`).
- A deliberately fatal client harness rig cannot do its fatal work inside its handler, given the engine transport's handler-exception handling (`../../../../Engine/Source/Agent/AGENTS.md`): `client_packet_fault_harness_rig` only arms its packet and `Game::ProcessGameMenuInput` delivers it outside that transport catch. Move and clear both the bytes and bound session before delivery so an exception or replacement session cannot leave the harness rig armed.
- Replay commands fail when `kbDebugInput` is disabled because the simulation will not consume those requests.
- `inject_payload` transfer entries are server-only debug controls, and their queue also seeds arrivals outside replay, so draining it stays independent of replay state. Keep their injected state deterministic.
- The game Agent owns replay transfer type classification, capture-count storage shape, and command JSON fields. The [engine replay harness rig](../../../../Engine/Source/Agent/AGENTS.md#architecture) owns how those counts are observed and when the classifier is invoked. `inject_payload` field keys are the member tokens named through `INJECTED_FIELD` in `Commands/ServerSimulationHarnessRigs.cpp`; a kind's accepted fields change only there.
- `edit_frame` keys are the `FRAME_COLUMN` tokens of each collection's column list in `Commands/ServerFrameEdit.cpp` and of each frame struct's `Values()`. A server-visible column added to or removed from a collection is added to or removed from that collection's list; the list's `static_assert` against its pair's `Members()` fails until it is. A server-visible collection pair added to any frame tuple, or an explicitly dispatched pair added beside `pPlayers` to both `ApplyEdit` `tuple_cat` calls, fails the server build until a `FrameCollection` specialization names it and its column list, the only per-collection code; add its name to the `edit_frame` collection names of [`commands-server.md`](../../Documents/AgentHarness/commands-server.md). A new `Values()` entry becomes writable unless `kRefusedFrameValues` names it; the `frame` key list of `commands-server.md` changes with it.
- `edit_frame` writes a cell's current CRC'd frame state directly, outside the tick input, so it is refused while recording, during playback, or with a pending replay transition, because no replay records the edit. Connected clients resynchronize through the Save entry point (`../Save/AGENTS.md`). Command contract: `../../Documents/AgentHarness/commands-server.md`.
- Commands that wait for a later frame, for the queue where messages wait for the renderer to pick them up, or for an input script use the engine deferred-response path. Ensure every deferred operation can resolve or fail without blocking the single in-flight channel.
- Scene queries are client-only and read render-visible state. Server frame queries read deterministic simulation state and must preserve collection/type validation.
- The frame registry keeps no rows, so nothing about it is enumerable or countable through a query. Its state reaches the harness only as the handle columns the collections themselves own, and the both-endpoint `registry_harness_rig` proves its behavior over its own fixed local data rather than over a frame.
