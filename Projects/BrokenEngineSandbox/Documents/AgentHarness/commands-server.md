# BrokenEngineSandbox Server Commands

[Back to AgentHarness hub](../AgentHarness.md)

### Server commands

- `status`: no params. Returns `{"tick","paused","recording","replaying","clientCount","activeCoords":[[x,y],...],"nextGlobalId","pendingFlagshipUpdateCount":int,"harvestedTransferTotal":int,"pendingTransferFixtureCount":int,"pendingAgentStatusChangeCount":int}`. `pendingFlagshipUpdateCount` counts restored or runtime-queued flagship navigation updates waiting for an advancing update. `harvestedTransferTotal` counts every transfer applied by a harvest since the current game state began, cumulatively; it is zeroed on load, reset, and entering replay playback, and does not move while paused or during playback. `pendingTransferFixtureCount` counts queued `inject_payload` transfer entries and `pendingAgentStatusChangeCount` counts queued `inject_payload` status-change entries; both include entries scheduled for a later `tick` until a drain releases them, and a transfer entry dropped at release leaves the count.
- `game_packet_fault_fixture`: server-agent-only parser-boundary fixture. The schema is exactly `{"case":"server_only"|"undersized"|"oversized"|"over_cap"}`; extra, missing, or non-string fields fail. It requires exactly one connected client with `bHandshakeComplete:true` and selects that client's `clientId` without a selector parameter. The command runs after the first `ServerSessionRuntime::Poll` has completed its `AfterNetworkPoll` parser and before `WaitForTick`; it clears the already-consumed `mReceivedGamePackets` and `mPendingDisconnects` bookkeeping, resets only the selected client's raw counter for `GamePacketType::kClientUpdatePlayerRequest` to zero for `over_cap`, appends the fixed entries below, and synchronously calls the existing game parser once. The pending-disconnect clear removes notifications already consumed by `AfterNetworkPoll`; after parsing, the fixture immediately consumes only a threshold notification it created before the next poll's normal clear. It does not exercise `AgentCommandsClient`, ENet sends, or a one-flush delivery window. The response is `{"clientId":int,"case":string,"type":int,"payloadSize":int,"fullSize":int,"entryCount":int}`.

  | Case | Type (`static_cast<uint8_t>`) | Payload bytes | Full size | Entries |
  |------|-------------------------------|---------------|-----------|---------|
  | `server_only` | `GamePacketType::kServerAssignPlayer` | 0 | 1 | 1 |
  | `undersized` | `GamePacketType::kClientUpdatePlayerRequest` | 12 | 13 | 1 |
  | `oversized` | `GamePacketType::kClientUpdatePlayerRequest` | 14 | 15 | 1 |
  | `over_cap` | `GamePacketType::kClientUpdatePlayerRequest` | 13 | 14 | 9 |

  All payload bytes are zero. The `over_cap` entries use the zero global ID, which is invalid and is discarded by the owned-player lookup. Its selected client's raw packet-type counter is reset to zero before the fixed burst; runtime accounting therefore starts from this fixture-controlled zero, not from ordinary shared-window scheduling. The frozen source comparison, not runtime inference, owns all four fixture conclusions: no gameplay mutation is attributed to the fixture, the sentinel/undersized/oversized entries return before dispatch, the first eight `over_cap` entries are admitted in order, and the ninth follows the existing over-cap policy within the shared update window.

  For live verification, set the server Network log level to Debug with `set_log_level {"category":"Network","level":"Debug"}` before each ordered baseline with `get_logs`; compare only appended lines. First run normal valid traffic and require no newly appended violation, corrupt-drop, or `game packet handler threw` lines in that bounded run. Then start a fresh session for each case with one handshaken client. Assert every fixture response field, then inspect only the selected client's connection/accounting state and the reason, packet type, and full-size fields in its Network violation log. Repeat the same command on that uninterrupted connection until the disconnect log reports the case's kind and limit: `server_only`, `undersized`, and `oversized` each record one corrupt-data strike and reach `Kind: corrupt Violations: 4` on the fourth invocation; `over_cap` records one too-fast strike and reaches `Kind: rate Violations: 8` on the eighth, provided all eight run within one minute of the first, because a too-fast strike is forgiven after a minute. Create a fresh session before the next case. Use `status`, `query_frame`, and `query_players` only as general normal-play health signals, not to claim hostile-fixture no-mutation equality.
- `engine_packet_fault_fixture`: engine-half counterpart of `game_packet_fault_fixture`, covering the wire dispatch that fixture never reaches. The schema is exactly `{"case":"truncated"|"size_mismatch"}`; extra, missing, or non-string fields fail. No build gate — it only drops a packet. It requires exactly one connected client with `bHandshakeComplete:true` and uses that client's ENet peer without a selector parameter, dispatching one packet synchronously through `Server::Receive`, so the admission gates, the dispatch `try/catch`, and `RecordContractViolation` all run. The response is `{"clientId":int,"case":string,"type":int,"size":int}`.

  | Case | Packet | Bytes | Failure | Recorded reason |
  |------|--------|-------|---------|-----------------|
  | `truncated` | `PacketType::kClientAcknowledgmentStream`, one declared entry | 10 | byte layout — the declared entry needs 27 more bytes than the packet carries | `corrupt payload`, from the dispatch catch |
  | `size_mismatch` | `PacketType::kClientAcknowledgmentStream`, one declared entry | 38 | semantic — the packet reads cleanly but its length disagrees with its declared entry count | `ackstream size`, from the handler cross-check |

  Both cases use `kClientAcknowledgmentStream` because its `10..1738` contract row is the one client-sendable engine row whose size range admits a packet the decoder can still reject for its length or byte layout: a fixed-size row's exact-size admission gate settles its layout before dispatch, though its handler may still reject a field value such as a negative tick, and the only other ranged row, `kClientHello` (21..101), always decodes because its fixed prefix is exactly the contract minimum and its trailing string and optional-GUID visitors never invalidate the reader. The two failures are mutually exclusive, so each packet is counted exactly once, and neither mutates server or game state.

  For live verification, set the server Network log level to Debug with `set_log_level {"category":"Network","level":"Debug"}` and take an ordered `get_logs` baseline before each case; compare only appended lines. Use a fresh session per case so the first invocation is that client's first violation and therefore logs the `Server::RecordContractViolation First` line carrying `Kind: corrupt` and the reason, packet type, and size above; both cases are corrupt-data strikes, and the policy logs nothing for repeats until the disconnect line at `Kind: corrupt Violations: 4`, so count repeats by driving the connection to that line rather than expecting one line per packet. Confirm the client stays connected and its next ordinary traffic is processed normally.
- `server_pre_handshake_ack_fixture`: server-agent-only Gate 4 preservation fixture with exact schema `{}`; arrays and any fields fail. It requires `kbDebugInput`, exactly one handshaken client, and enough room in that client's current admission window for one packet and the fixed 10-byte zero-entry `ClientAckStreamMessage`. It snapshots the selected client and peer, handshake, violation and ACK packet-type counts, every slot's ACK state, ACK-stall fields, and echoed timestamp. It then temporarily clears the handshake under scope-guarded restoration and synchronously delivers the valid ACK through `Server::Receive`. The real Gate 2 adds exactly one packet and 10 bytes before the real Gate 4 logs and drops the ACK; the fixture restores and relooks up the client before checking all other snapshotted state. Returns `{"clientId":int,"type":int,"size":10,"packetCountBefore":int,"packetCountAfter":int,"byteCountBefore":int,"byteCountAfter":int,"handshakeRestored":true,"clientPreserved":true,"peerPreserved":true,"typeCountUnchanged":true,"ackSlotsUnchanged":true,"ackStallUnchanged":true,"timestampUnchanged":true,"contractViolationsUnchanged":true}`. Any failed preservation check returns the ordinary command failure envelope instead.

  For live verification, set the server Network log level to Debug with `set_log_level {"category":"Network","level":"Debug"}`, take an ordered `get_logs` baseline, and invoke the fixture once with one connected client. Require one appended `Server::Receive pre-handshake drop` line naming the response's `clientId` and raw `type`. Require `packetCountAfter == packetCountBefore + 1`, `byteCountAfter == byteCountBefore + size`, `size == 10`, and every Boolean result to be true. Then require `status.clientCount == 1` and ordinary client traffic to continue on the same connection.
- `pause`: `{"paused":bool}`. Returns the applied `paused` value.
- `timescale`: `{"faster":bool}`. Steps the shared timescale and returns `{"numerator","denominator"}`. The slowest step is 1/32; `{"faster":false}` there changes nothing and still succeeds.
- `save`: `{"file"?:"bare filename"}`; defaults to quicksave. Rejects empty names, NUL, separators, `..`, `:`, and Windows device basenames. Returns `{"file"}`.
- `load`: `{"file"?:"bare filename","pauseAfterLoad"?:false}`. `pauseAfterLoad` must be Boolean when present; invalid parameters fail before loading or resetting and do not change pause state. Missing/corrupt/truncated data resets fresh while returning success. Absent/false leaves the normal post-load state unpaused; true atomically pauses after a successful load or completed fresh fallback, before frame inputs can be constructed. Returns `{"file","resetToFresh":bool,"paused":bool,"pendingFlagshipUpdateCount":int}`.
- `reset`: no params. Resets the fresh game and fleet manager. Returns `{}`.
- `replay_record`: `{"start":bool}`. Schedules or cancels an idempotent recording transition and returns `{"pending":bool}`. Poll `status.recording` for the effective transition. `{"start":true}` fails while playback is active or pending. Requires `kbDebugInput`.
- `replay_play`: no params. Starts playback or cancels active playback and returns `{"pending":true}`. Fails while recording is active or a record start or stop is pending. Poll `status.replaying`. Per-tick checks call `DifferenceStreamReader::ValidateChecksum`; mismatch logs `LogDifferences CRC Client: ...`. Readers retire independently. When the last reader reaches its endpoint, the server logs `End replay <tick>, looping` at `Default/Debug` and loops; playback never ends by itself. Requires `kbDebugInput`.
- `replay_transfer_capture`: no params. Returns `{"firstWriterInputTick","writerInputCount","events":[{"recordingEventTick","playbackEventTick","playerCount","spaceshipCount","blasterCount","missileCount"}]}`. `firstWriterInputTick` is `-1` until observed. `events` holds one entry per recording event tick in capture order, each entry's counts summed across the destinations of that tick; it holds every captured event of the recording and clears at recording start and whenever the fixture snapshot is cleared (reset, and any recording or playback failure, cancellation, or abort). It is kept after a successful stop and is carried into playback. An entry's `playbackEventTick` is `-1` until playback applies that entry's record and then equals its `recordingEventTick`. A transfer captured after dispatch at `E` is recorded at `E` in the post-dispatch channel and published/replayed at `E`. During playback, an entry's `playbackEventTick` is latched from the exact tick whose post-dispatch record the reader loaded and applied. If the `set_log_level` response reports effective Network `Verbose`, use `ServerBroadcaster::BuildTickPublication` as runtime publication evidence; if the requested level is clamped to `Debug`, that kVerbose line is unavailable and the static source/phase trace owns publication-at-`E`. In both cases, runtime acceptance uses the event ticks, final state/count, checksum/no-desync signals, and completed replay loop; status/query results are not historical timing evidence. `writerInputCount` is the total normal-writer update ticks since a successful recording start; terminal flushes do not increment it. Requires `kbDebugInput`.
- `replay_drop_retained_end_frame`: `{"coord":[x,y]}`. During recording, removes the retained terminal frame from that coordinate's most recently terminalized generation: the last generation when it is terminal, otherwise the generation immediately before the open last generation. Returns `{"coord":[x,y],"dropped":true}`. Requires `kbDebugInput`.
- `replay_inject_persistence_failure`: `{"stage":"invalidation"|"grid"|"transfer_capture"|"coordinate_writer"|"fullframes_record"|"metadata"|"inventory"|"final_manifest","coord"?:[x,y]}`. `coordinate_writer` and `fullframes_record` require `coord`; every other stage rejects it. `invalidation` and `grid` require inactive recording; every other stage requires active recording. `transfer_capture` invalidates recording when the next accepted transfer batch reaches replay capture, before a writer is created or changed; the live transfer still proceeds. `coordinate_writer` and `fullframes_record` resolve their target when armed: they select the open last generation when present, otherwise the most recently terminalized generation with retained state. A later generation append cannot redirect either failure. After the selected writer saves, `fullframes_record` atomically truncates its nonempty `.fullframes` file by one byte before inventory hashing; a mutation I/O failure deletes that writer's complete sibling set and prevents manifest publication. `inventory` is consumed immediately before final artifact hashing and manifest publication. Returns `{"stage","coord"?:[x,y],"armed":true}`; the response does not expose a generation selector. Requires `kbDebugInput`.
- `query_frame`: `{"coord":[x,y]}` for a loaded, ready cell. Returns counts under `players`, `spaceships`, `missiles`, and `blasters`.
- `query_players`: `{"coord":[x,y],"offset"?:0,"limit"?:256}`. A negative `offset` or `limit` is a parameter error. Returns `{"total","players":[{"index","uuid","globalId","local":[x,y,z],"dir":[x,y,z],"armor","shield","flags":int,"alignment"}]}`. Every row belongs to the requested cell, so `local` is meters from that cell's center and no row repeats the coordinate.
- `query_collection`: `{"coord":[x,y],"collection":"spaceships"|"missiles"|"blasters","offset"?:0,"limit"?:256}`. A negative `offset` or `limit` is a parameter error. Returns `{"total","items":[...]}`. Spaceship rows: `index,local,dir,health,deltaRotation,alignment,registryId`; missile rows: `index,local,dir,deltaRotation,deltaRotationDelay,alignment,registryTargetId`; blaster rows: `index,local,dir,alignment`. `local` is meters from the requested cell's center. `registryId` is the spaceship's frame registry handle and `registryTargetId` is the registry handle the missile is homing on, so a live missile's nonzero `registryTargetId` matches a spaceship `registryId` in the same cell, or one that spaceship cleared later in the same tick (death, destroy, or transfer) and the missile drops at its next Update; `0` means no target. `deltaRotation` is the live turn rate; a missile's `deltaRotationDelay` counts down through zero and stays negative after its launch ramp finishes.
- `query_profile`: server-only CPU profile query. `params` must be `{}` or exactly `{"ackActivationEventSequence":<nonzero unsigned integer>}`; arrays, non-objects, signed/float/string/zero acknowledgements, and unknown keys fail before any profile read or acknowledgement. It returns raw `timers[{index,name,currentUs,averageUs,maxUs,allocations,threads}]` and `counters[{index,name,count}]`, including zero rows hidden by the Profile UI. On a server built with `kbProfiling`, only the `NavQuery` timer row additionally returns `sampleSequence`, `sampleUs`, `queryCount`, `aStarCount`, and `activationEvent:{available,eventSequence,sampleSequence,sampleTick,sampleUs,queryCount,aStarCount,qualifying,overrun}`. `qualifying` is `available && queryCount == 8 && aStarCount == 8`; it is presentation logic, not an Engine event gate. An acknowledgement request also adds `activationEventAcknowledged` to that row (`true` only when the exact available event sequence was cleared). The timer row and event are read under one profile mutex, so the post-ack fields are coherent. `sampleSequence` starts at `0` and advances once per accepted normal one-tick update; `sampleUs` is the accumulated timed `NavQueryDirection` duration latched after all active-cell workers join, `queryCount` counts timed calls, and `aStarCount` counts calls that entered A*. Repeated reads before a newly accepted tick return the same raw sequence and values. An available event's sample payload and event sequence are immutable across reads; a later candidate sets only its separate sticky `overrun` bit. An exact acknowledgement clears `available` and `overrun` without rewinding the event sequence or retained payload; stale/future acknowledgements change nothing. Paused, burst, non-`1/1` timescale, save, replay, zero-tick, and other rejected/no-dispatch paths discard pending raw values and cancel an unpublished arm/floor without changing a retained event. Polling can skip raw sequence values; skipped values are unobserved gaps, not rejected-update records. The client `query_profile` remains `{}`-only and carries no activation fields; its response is documented in `commands-client.md`.
- `inject_payload`: `{"entries":[...],"navQueryActivation"?:{"arm":true},"pauseAfterWriterInput"?:bool}`; these are the only top-level keys, and `entries` is a non-empty array. It queues player status changes into a cell's tick input and cross-cell transfer arrivals into a cell's transfer harvest. The whole batch validates before anything is queued or any global id is minted, so a rejected batch changes no pending count and leaves `status.nextGlobalId` unchanged. Each entry is `{"coord":[x,y],"type":<type>,"tick"?:int,...fields}` with a `type` from the table below; a key other than `coord`, `type`, `tick`, and that type's fields fails the batch. Field keys are the payload member names in `Frame/StatusChange.h`, verbatim. Values by member type: `bool` a JSON boolean; `int64_t` a JSON integer; `uint8_t` a JSON integer in `[0,255]`; `float` a finite number; a `std::chrono::duration<float>` (the `...Seconds` members) a finite number of seconds; `engine::GridCoord` an `[x,y]` grid coordinate; `XMVECTOR` an `[x,y]` pair of finite numbers in the cell's local frame, a position being meters from the cell's center, whose z and w the server sets.

  | `type` | Fields | Also requires |
  |--------|--------|---------------|
  | `SpawnPlayer` | `fSpawnOffsetX`, `fSpawnOffsetY`, `bIsFlagship`, `fleetWantedCoordinate` | active `coord` |
  | `DestroyPlayer` | `iPlayerUuid` (required) | active `coord` |
  | `UpdatePlayer` | `iPlayerUuid` (required), `bUseMissiles`, `navigationDelaySeconds` | active `coord` |
  | `UpdateFleet` | `iPlayerUuid` (required), `fleetWantedCoordinate` (required), `bIsFlagship` | active `coord` |
  | `TransferPlayer` | `vecPosition`, `vecDirection`, `vecVelocity`, `fHealth`, `fShield`, `nextBlasterFireTimeSeconds`, `nextSecondarySpawnTimeSeconds`, `shieldCooldownSeconds`, `shieldDownSoundCooldownSeconds`, `animationTimeSeconds`, `navigationDelaySeconds`, `fleetWantedCoordinate` | `kbDebugInput`; creates a missing `coord` |
  | `TransferSpaceship` | `vecPosition`, `vecDirection`, `vecVelocity`, `fHealth`, `nextBlasterSpawnTimeSeconds`, `fDeltaRotation` | `kbDebugInput`; live `coord` |
  | `TransferBlaster` | `vecPosition`, `vecVelocity`, `uiTypeIndex` | `kbDebugInput`; live `coord` |
  | `TransferMissile` | `vecPosition`, `vecDirection`, `vecVelocity`, `fAcceleration`, `deltaRotationDelaySeconds`, `timeSeconds`, `nextJitterSeconds`, `fDeltaRotation`, `fDeltaRotationMaximum`, `fPitch` | `kbDebugInput`; live `coord` |

  `iPlayerUuid` is a `query_players` `uuid`, which changes when the player crosses cells. A live `coord` holds a player or an active client subscription. An omitted field takes its payload struct default (`fSpawnOffsetX` 45, `fSpawnOffsetY` -12, `navigationDelaySeconds` 60), except that `fleetWantedCoordinate` defaults to `coord`, and a transfer's `vecPosition` defaults to the cell center, `vecDirection` and `vecVelocity` to `[1,0]`, `fHealth` and `fShield` to 1, `uiTypeIndex` to the player blaster type, and `fDeltaRotationMaximum` to 2. The server sets the rest: a minted global id for `SpawnPlayer` and `TransferPlayer`, the player alignment, an empty client GUID, zero player flags, and the pending countdown ticks. An injected player is therefore synthetic AI and not an ownership fixture. A spawned player starts with `kUseMissiles` clear; an `UpdatePlayer` entry with `bUseMissiles:true` takes effect one second (`kiTickRate` ticks) after the tick it enters.

  The batch also fails during replay playback, on a transfer entry without `kbDebugInput`, on a non-finite value, on a `SpawnPlayer` offset or a transfer `vecPosition` outside the cell, on a `TransferPlayer` `vecVelocity` whose XY length exceeds `kfPlayerMaximumSpeed` (33.33 m/s), on a `navigationDelaySeconds` outside `[0,60]`, on a `nextBlasterFireTimeSeconds` outside `[0,kfBlasterFireInterval]`, and on a `uiTypeIndex` that is not an adoptable blaster type. The command makes no terrain check; a blaster destroys itself on terrain contact, so a `TransferBlaster` that must survive needs a terrain-clear `vecPosition` (the probe in [replay.md](replay.md#replay-transfer-capture-fixture)). To send a player out across a cell's east edge, queue `{"coord":<cell>,"type":"TransferPlayer","vecPosition":[433.86,0],"vecVelocity":[33.33,0]}`: 433.86 m is half the cell width (`cell_coordinate_probe` `area.width`) less 15.5 ticks of travel at `kfPlayerMaximumSpeed`, so the arrival coasts under its post-arrival transfer lock and crosses into the eastern neighbor about 16 ticks after its harvest through the ordinary transfer producers. Terrain near that path can push the coast off its line; then pick another cell.

  `tick` is an absolute `status.tick` value and must be a JSON integer greater than the current `status.tick`; omitted, it means the next tick, `status.tick + 1`. A status change enters the input of exactly its target tick, and a transfer is harvested at exactly its target tick, at any timescale and in catch-up bursts that run several ticks per update; a pause stops the clock, so entries wait. A status-change entry whose coordinate is inactive or whose frame is not ready at its target tick stays queued and applies on the first later tick that can take it. A non-player transfer entry whose destination is no longer live at its target tick is dropped with a Network warning. An active recording captures released entries as it captures natural ones: status changes in their tick's input, transfers in the post-dispatch channel. Load, `reset`, and session replacement clear both queues. Recording stop, a recording-start failure, cancelling a not-yet-started recording, and a replay transient-state clear drop every queued transfer entry, future-tick ones included, while queued status-change entries survive.

  `pauseAfterWriterInput` requires `kbDebugInput` and must be a JSON boolean whenever present; the response echoes it. `false` imposes nothing further and arms nothing. `true` also requires a transfer entry in the batch, active recording or a paused, unconsumed `replay_record {"start":true}`, no automatic pause already armed, and no entry carrying `tick`. After queueing, `true` arms count `1` for a pending start, or snapshots the active writer-input count `N` and pauses at `N + 1`, the writer input of the event tick whose post-dispatch record is written later in the same update.

  `navQueryActivation` must be exactly `{"arm":true}`: unknown nested keys, a non-object value, or any `arm` value other than JSON boolean `true` fails the batch before profiler state or queue mutation. The arm is server/profiling-only and also requires unpaused normal state (`kPaused`, `kSaveReplay`, and `kLoadReplay` clear; timescale `1/1`; recording and replay inactive), no transfer entry, and no entry carrying `tick`. The handler captures its own `queuedAtTick`, computes `minimumSampleTick = queuedAtTick + engine::kiTickRate + 1`, arms and queues the validated batch as one main-thread transaction, and rejects an occupied retained event or sticky overrun before queueing anything. Arming while an earlier arm is still pending (armed, not yet published or cancelled) is a caller error: it logs `Assert failed`, returns `ok:false` with that text, and changes neither the pending arm nor the queue.

  The response is `{"injected":int,"globalIds":[...],"deferred":bool}`. `globalIds` lists the ids minted for `SpawnPlayer` and `TransferPlayer` entries in entry order, and `deferred` is true while the server is paused. An armed request adds `"navQueryActivation":{"armed":true,"queuedAtTick":int,"minimumSampleTick":int}`, and a request carrying `pauseAfterWriterInput` adds its echo.

Every server `[x,y]` grid-coordinate parameter (`coord`, `fleetWantedCoordinate`) must hold two JSON integer literals, with no fraction or exponent, within the signed 32-bit range; any other component, including a whole-valued `1.0` or `1e0`, fails the command before that coordinate is looked up or used, before that entry mints an ID, and before anything is queued.

`inject_payload` fails during replay playback. While paused, it remains accepted and queued; `deferred:true` means each entry applies on the next unpaused tick, or on its `tick` when that is later. A speculative client reconciliation line after that tick is not a confirmed desync; only `CONFIRMED DESYNC after full rollback/replay` proves one.

Pause/timescale persist on an empty server. They reset only when the last connected client disconnects. A client may join a paused server and render frozen state, but spawning still needs an unpaused tick.

Frame-read schemas/extractors (`query_frame`, `query_players`, `query_collection`) are owned by `AgentCommandsServerQueries.cpp`. CPU `query_profile`, simulation control, and server dispatch remain in `AgentCommandsServer.cpp`; replay and injection live in `Commands/ServerSimulationFixtures.cpp`.

## Durable caveats

- `navQueryActivation` is sticky until its exact event sequence is acknowledged. Do not issue another armed transition while `activationEvent.available` is true, or while an earlier arm is still pending; the pending case asserts. A pending arm that never publishes (no accepted tick at or after its floor with a query count of eight) blocks re-arming until a false latch (below) cancels it, for example a pause. A retained event is one immutable payload, not a history: an additional query-count-eight candidate cannot overwrite it and sets only `activationEvent.overrun`; treat `overrun:true` as measurement failure. A false latch (pause, non-`1/1` timescale, burst/catch-up, save/replay, zero-tick, or replay no-dispatch), shared reset/load, and replay-load entry cancel only an unpublished arm/floor and clear pending raw values; they preserve a retained payload, sequence, and sticky overrun. The client command surface and client profile schema remain unchanged.
- Server frame-read query schema and extraction live in `Projects/BrokenEngineSandbox/Source/Agent/AgentCommandsServerQueries.cpp`; simulation control, CPU `query_profile`, and dispatch live in `AgentCommandsServer.cpp`; replay and injection live in `Commands/ServerSimulationFixtures.cpp`.
