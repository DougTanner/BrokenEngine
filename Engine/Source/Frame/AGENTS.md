# Frame - Base Simulation State

## Overview

Engine-owned frame state, fixed-tick phase orchestration, per-cell static data, collision, terrain sampling, navigation, and generic collections. Game-specific phase extensions live in the project Frame (`../../../Projects/BrokenEngineSandbox/Source/Frame/AGENTS.md`).

Update Frame Update Pipeline (`../../../Documents/Architecture/FrameUpdatePipeline.md`) when phase ordering or participation changes.

## Architecture

- `RunFrameTick` and `ActiveFrameRef` are engine-owned; `RunFrameTick` verifies the required floating-point environment before advancing deterministic state, and the shared CRC is stamped after the tick phases and before server transfer harvest. Phase order and the dispatch paths sharing the core are in Frame Update Pipeline (`../../../Documents/Architecture/FrameUpdatePipeline.md`); the phase bodies are game-implemented (`../../../Projects/BrokenEngineSandbox/Source/Frame/AGENTS.md`).
- `FrameInterpolateBase` owns continuous state used for fixed-tick interpolation; `FramePostRenderBase` owns committed deterministic state and per-tick queues. Fixed-tick Interpolate state may feed `FramePostRenderBase` and shared CRC state; shared PostRender/CRC state must not derive from a client render-interpolated frame or client-only collection member. Stop when a proposed source crosses or obscures this boundary.
- Static cell data is derived from the grid coordinate and packed island assets. A cell's frame area is derived data with one canonical value, never input to validate or reject: every site that reads it from a save file or a network payload recomputes it with `ComputeCanonicalFrameArea(coord)` instead of trusting the stored or received value, and every producer must agree with that value. Elevation is shared; navigation data is server-built and sent to clients. Navigation implementation spans `NavBuild.cpp` (template contour bake), `NavCellData.cpp` (cell merge, visibility, acceleration, serialization), and `NavQuery.cpp` (runtime queries).
- Collision and area-damage queues are thread-local because coord ticks may run in parallel. Their `thread_local` containers must be default-constructed empty: those constructors run during `mi_process_init` (the mimalloc allocator's own process-startup step), before the allocator is ready, so pre-allocating at construction crashes at process start. Size them on first use instead, wrap that resize and any later data-dependent growth in `ScopedSuppressAllocationTracking`, and on overflow `DEBUG_BREAK` naming the pre-allocate constant to raise. The one exception is the collision layer count, which is fixed at compile time, so overflow there logs `kError` and asserts rather than growing. The same rules apply to any new thread-local simulation scratch.
- An entity's position must lie inside its own cell's bounds. A position outside them belongs to a neighbouring cell, which is why an out-of-bounds entity transfers instead of being simulated locally, and why a spawn request naming a point outside the cell is refused rather than clamped.
- The produce and consume windows are fixed, not merely ordered: area damage is added during the PostCollision phase and queried during the AreaDamage phase, and each queue is cleared at the end of the phase that owns it. Adding from the AreaDamage phase, or querying from Update, silently drops the hit or delivers it a tick late.
- Collision gathers candidate events across every layer pair, then sorts them globally by time of impact with the layer and object indices as tiebreakers so the order is total and reproducible, and commits each accepted event to both sides. An object flagged destroy-on-collide accepts only its earliest event. Optional per-object maximum-time cutoffs are exclusive, which lets callers reserve exact-time ties for terrain and frame-boundary outcomes. Per-pair collision masks must be bi-directional and same-layer collision is unsupported; both are asserted.
- Large terrain/nav allocations are lazy. Do not make frame constructors allocate proportional to world or mesh size.

## Frame Registry

- `FrameRegistry.h`/`.cpp` let one collection find rows of another without duplicating them. It binds columns the collections already own, copies no entity records, allocates nothing, and keeps no state between query windows, so nothing it produces is serialized, CRC'd, or transferred.
- The game builds both query windows and owns their timing, bound columns, and batch storage (`../../../Documents/Architecture/FrameUpdatePipeline.md`, `../../../Projects/BrokenEngineSandbox/Source/Frame/AGENTS.md`). The engine never names a game collection.
- The caller owns one combined workbuffer reservation per query window and keeps it alive until the context is destroyed; form every pointer and span the context uses only after it returns. The reservation holds the source-row indices, registry scratch, and layer descriptors; no workbuffer allocation or growth is allowed while a context is live. `RegistryScratchBytes` sizes only the eligible-row and subscriber-count storage, whose `uint16_t` counts assert before the 65,536th subscription so ranking state cannot wrap. `RegistryBatch::rows` and `results` are caller-provided. A context never survives source-layer movement, reallocation, or cell transfer.
- Source ids are unique across every bound layer and eligible row spans are strictly ascending and in range; debug builds validate both when the context is built.
- Acquisition is a deterministic direct scan feeding CRC'd state: one fixed ranking — fewest subscribers, then smallest angle, exact ties by layer order then row order — always bounded by the caller's radius. Alignment filtering needs the source and consumer alignment columns both bound. Changing that order changes simulation results.
- `AssignRegistryClientGuid` is the registry's only write. It is legal only on the main thread after the tick, through an ownership layer whose client-GUID column is CRC-excluded. The caller holds that layer by value and never retains it across a tick, a transfer, or a reallocation.

## Collection and Serialization Invariants

- `Collections()` order is a dependency order, not just a type list. A producer must precede an owned consumer; Explosions before SmokeTrails is the live example. Tuple-size and client/server type checks do not verify this ordering.
- `Write()`/`Read()` walk full `Collections()` and are build-local. Cross-build server snapshots use `ServerRead()` with `ServerCollections()` and shared members. Preserve tuple order, type parity, and member wire order together.
- Collection-level SOA, initialization, ID-map, count, and CRC rules are authoritative in Collections (`Collections/AGENTS.md`).

## Terrain and Navigation

- An island-free cell is a supported state whose elevation samples all return the sea floor (no grid is built) and whose navigation data is built empty.
- World cells place and rotate islands deterministically, from independent RNG streams seeded from the grid coordinate with distinct multipliers; each stream's draw order is load-bearing, so preserve each stream's purpose and draw order; separation keeps one category from directly consuming another's RNG state, but placement control flow can still change later draws. The generator caps each cell at 107 placements; static-data deserialization rejects a larger count before resize/publication, and client rendering derives its aggregate placement arena from that cap and the active-cell subscription slots plus one local unconfirmed cell. Keep world/local transforms, the placement bound, and the west/east/north/south convention consistent across CPU sampling and shaders.
- Two terrain-sampling paths exist and must not be mixed. Simulation code calls `FrameElevation`/`FrameNormal`, which read only the cell's own `FrameStaticData` elevation grid, never `mCoordFrames`, and never cross into a neighbouring cell, keeping parallel per-cell ticks from racing the tick-time grid build. Render and other non-tick code calls `GlobalElevation`/`GlobalNormal`, which walk `mCoordFrames` and must never run from frame-tick code; both assert on it.
- CPU and GPU terrain elevation deliberately disagree below sea level: `TerrainElevation.frag` applies a depth-compression curve to undersea samples that no CPU path mirrors, while the CPU folds raw max-blended samples from packed height data. That texture feeds downstream shaders only, is never read back, and the simulation never consumes its curved values, so neither side reaches the CRC. Do not port the curve into `CellElevation`: it would change CRC'd sim positions for a purely visual effect. Do not assert stronger guarantees about the texture's sampling format here.
- Client terrain residency keeps the shared heightmap and hull resident but decommits each template's CPU mesh slice whenever it is not being restored. Coordinate texture and mesh restoration or eviction only in the renderer's window after all pending adds and removes have been processed; this visual residency stays outside deterministic CRCs. Renderer teardown invalidates its mesh allocations without cancelling File-owned range-reload state.
- The obstacle visibility graph is built once per cell, in world space, over every obstacle polygon the cell contains; island templates contribute contour geometry only. Per-template building yields the disjoint union of per-island graphs, leaving inter-island routes unreachable. Because the graph spans the cell, an A* miss is unexpected: disconnection is the usual cause, and a found path whose first waypoint coincides with the start also reports as a miss.
- The build path and the runtime query share one segment-blocked and one point-in-polygon predicate through `NavBuildInternal.h`. Keep them shared: a divergent epsilon or boundary rule lets the graph claim a segment the query rejects, threading paths through obstacles.
- Navigation deserialization is a trust boundary and rejects a corrupt stream before the acceleration structures are rebuilt: every vertex coordinate finite, the polygon offsets ascending from 0 and partitioning the vertices at three or more per polygon, every visibility-edge endpoint indexing a vertex that was read. The acceleration build, runtime queries, and debug nav rendering rely on that guarantee and must not re-validate it.
- The contour bake takes its clearance distance and elevation threshold as caller-supplied values; the game derives both and the server passes them in during startup, and the bake forwards them unchanged. Engine navigation code must not reach back into game constants for them.
- Frame and gameplay geometry uses meters (one meter per engine unit); UV is only the normalized template representation. For navigation contours, union in UV, convert to centered local meters with the template's anisotropic footprint, apply clearance and simplification there, then map back to UV for storage; a scalar offset in UV makes the world-space margin depend on the footprint.
- World-space nav polygons wind clockwise, because placing a template mirrors Y; the template's own UV-space contour winds counter-clockwise. Derive orientation-dependent tests such as vertex convexity from measured winding rather than assuming the counter-clockwise convention the placement hulls carry.
- Navigation version changes invalidate derived data and contribute to the game frame version.
