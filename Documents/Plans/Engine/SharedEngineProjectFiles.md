# Move Engine/Common project membership and shared build settings into engine-owned Visual Studio files

## Context

A second game project will be created beside `Projects/BrokenEngineSandbox`, and shared code is not to be duplicated per project (user decisions, this session; agent record). Today every engine and Common file and every build setting lives inside the two Sandbox projects, so a second game would copy about 1,400 lines of project XML, and every later engine file addition would have to edit every game's projects.

Evidence, verified at baseline `f1d140ae` (line numbers approximate):

- Membership. `Projects/BrokenEngineSandbox/Platforms/VisualStudio2026/BrokenEngineSandbox.vcxproj` holds 515 `ClCompile`/`ClInclude`/`None` items: 377 under `..\..\..\..\Engine\` (engine source, the client-only GLSL `None` items, and the engine dual-language layout headers under `Engine\Data\Shaders\`), 47 under `..\..\..\..\Common\`, 83 game `..\..\Source\` items, one game `..\..\Data\Shaders\ShaderLayouts.h`, and 7 `$(GameDataDirectory)\*.h` generated headers. `BrokenEngineSandboxServer.vcxproj` holds 260: 140 Engine, the same 47 Common, 67 game, 6 generated headers. `Engine\Source\Pch.cpp` carries per-configuration `PrecompiledHeader` `Create` metadata in both (client `:667-670`, server `:517-520`). The two `.vcxproj.filters` mirror these under the `Engine\`, `Common\`, `Game\`, and `DataFiles` roots. No `.props` or `.vcxitems` file exists in the repository (`git ls-files '*.props' '*.vcxitems'` is empty), and both projects carry an empty `<ImportGroup Label="Shared">` (client `:50-51`).
- Settings. ## Design

The author recommends this shape; each choice carries its rationale.

1. New engine-owned directory `Engine/Platforms/VisualStudio2026/`, matching the `<Component>/Platforms/VisualStudio2026/` layout of DataPacker, ThirdParty Prebuilts, and the tools. It holds:
   - `EngineClient.vcxitems` + `EngineClient.vcxitems.filters` — a Visual Studio shared items project (Globals with a new `ItemsProjectGuid`, `HasSharedItems`, and the `SourceItemsFromImports` project capability) holding every item the client project carries today under `Engine\` and `Common\`, including the GLSL `None` items, the engine layout headers, and `Pch.cpp` with its `Create` metadata. Item paths use Visual Studio's shared-item form `$(MSBuildThisFileDirectory)..\..\Source\...` (Engine) and `$(MSBuildThisFileDirectory)..\..\..\Common\...` (Common). Filters keep today's names (`Engine\<path>`, `Engine\Data\Shaders\<sub>`, `Common[\<sub>]`) and may reuse today's filter GUIDs.
   - `EngineServer.vcxitems` + `EngineServer.vcxitems.filters` — the same for the server's 187 Engine and Common items. Rationale for two whole lists over one both-sides list plus two one-sided lists: it keeps the client/server pairing `/update-vcxproj` already resolves (a `both` file is one item in each list, as today), so the resolver's roles and the pair validation keep their model.
   - `Engine.props` — every setting the two Sandbox projects share today after `Microsoft.Cpp.props`: the Data property group, the per-configuration `OutDir`/`IntDir`/`TargetName`/`CustomBuild*Targets`/`LinkIncremental`/analysis/clang-tidy property groups, `ClangTidyChecks`, `ClangTidyToolExeAdditionalOptions`, the three `ItemDefinitionGroup`s, and the `ValidateDataBuildProperties` target. Move them verbatim per configuration, without merging the three configurations, so the diff stays reviewable and the command-line comparison below is exact. Keep every path expression byte-identical (`$(ProjectDir)\..\..\..\..\...` for repository paths, `$(ProjectDir)\..\..\Source` and `\..\..\Data` for game paths, `$(SolutionDir)...` in `PreBuildEvent`). Rationale: compiler and linker command lines stay byte-identical, `Test-IncludeOrder.ps1` keeps parsing `$(ProjectDir)` entries, and the depth is already fixed by the standard layout in `Projects/AGENTS.md` (`DataRepositoryRoot` already relies on it). This departs from the audit's proposed `$(MSBuildThisFileDirectory)` form for settings, recorded in Notes.
   - `BrokenEngineAnalysis.ruleset`, moved (`git mv`) from the Sandbox directory because `CodeAnalysisRuleSet` resolves `$(MSBuildThisFileDirectory)` against the file that sets it, which becomes `Engine.props`.
   - `AGENTS.md` — the shared build hub (item 4).
2. Client/server selection: each game `.vcxproj` sets one property, `EngineTarget` (`Client` or `Server`), in its Globals group. `Engine.props` derives from it the `BT_CLIENT`/`BT_SERVER` define (kept at its current position, after `BT_ENGINE`), the client-only RenderDoc include entry as its own `;`-separated property entry at its current position in the list, the client Profile `EnableClangTidyCodeAnalysis=false`, and the client-only Debug/Profile `RunCodeAnalysis=false`. `ValidateDataBuildProperties` gains one `Error` for an `EngineTarget` other than `Client` or `Server`, because without it a game project that omits the property builds with neither define and no diagnostic. Drop the steamworks library directory from all six `AdditionalLibraryDirectories` as it moves into the props file.
3. Each Sandbox `.vcxproj` keeps only: `ProjectConfigurations`, Globals (`ProjectGuid`, `RootNamespace`, `WindowsTargetPlatformVersion`, `EngineTarget`), the `Microsoft.Cpp.Default.props` import, the `Label="Configuration"` property groups (they must precede `Microsoft.Cpp.props`, which a props file imported after it cannot do), the `Microsoft.Cpp.props` import, `<Import Project="..\..\..\..\Engine\Platforms\VisualStudio2026\EngineClient.vcxitems" Label="Shared" />` (server: `EngineServer.vcxitems`) inside the existing `ImportGroup Label="Shared"`, an `Engine.props` import after the user props in each configuration's `PropertySheets` group (same evaluation position as today's inline settings), its game items and the game `ShaderLayouts.h`, the `$(GameDataDirectory)\*.h` generated headers (the game's data path; the server still omits `Shader.h`), and the `Microsoft.Cpp.targets` import. Its `.filters` keeps only the `Game\` tree and `DataFiles`; the empty leftover server `Engine\Graphics` filter is dropped with the rest of the `Engine\` declarations. Each `.sln` gains its shared items project entry and the `SharedMSBuildProjectFiles` section Visual Studio writes for a shared items reference, so Solution Explorer shows the engine items under that node with their filters. A shared items project has no build configurations, so building the solution still builds one executable.
4. Docs move by ownership: the engine-wide content of the Sandbox VS `AGENTS.md` (`## Build Configuration` in full, `## vcxproj File Inclusion Rules`, the `Engine\` and `Common\` roots of `## vcxproj.filters Rules`, and the server-content paragraph of `## Client and Server Projects`) moves to `Engine/Platforms/VisualStudio2026/AGENTS.md`, which also states how a game project consumes the shared files (`EngineTarget`, the two imports, the standard-layout depth the props file assumes). The Sandbox VS `AGENTS.md` keeps its Overview, the two project names with their `EngineTarget`, the `Game\` filter root, and the generated-header `DataFiles` rule, routing to the hub for the rest. Every route listed under Ownership docs in Context is repointed to the hub section that now owns each fact. The `Get-AffectedAgentsDocs.ps1` override moves to the hub path; the Sandbox entry is removed when the slimmed doc fits its computed budget.
5. Tooling:
   - `Test-IncludeOrder.ps1` `Get-IncludeDirectory`: for a game project (and the `Engine|Common` row), read the list text from `Engine/Platforms/VisualStudio2026/Engine.props` and expand `$(ProjectDir)` against the game project's directory; skip the RenderDoc property entry like any non-`$(ProjectDir)` entry (its only consumer, `Common/ExternalHeaders.h`, is excluded and resolves through the ThirdParty root anyway). The `Engine|Common` binding to the first discovered game stays as it is; the shared items do not change it. DataPacker and tool rows are unchanged.
   - `Test-VcxprojPair.ps1`: accept a `.vcxitems` path with an adjacent `.vcxitems.filters`, running the same checks.
   - `Resolve-VcxprojMembership.ps1`: output schema and role values unchanged; correct the row-1 detail text so engine shaders name the engine client item list and game shaders the game client project.
   - `update-vcxproj` `references/worker.md`: the ownership table states that for `Engine/Source/**`, `Common/**` (game side), and engine `Data/Shaders` rows the `client`/`server` role means `EngineClient.vcxitems`/`EngineServer.vcxitems`, and for game rows the game `.vcxproj`; step 3 runs `Test-VcxprojPair.ps1` on each affected pair, including a `.vcxitems` pair.
   - `Get-SessionChangeInventory.ps1` `:243`: class `.vcxitems`, `.vcxitems.filters`, and `.props` as `vcxproj`.

Risk tier: Tier 3. Triggers (`.agents/references/risk-tiers.md`): build/bootstrap coordination that can block other sessions — every session's client and server build, the primary Visual Studio build, and every later `/update-vcxproj` run go through the new files, so a wrong import, dropped setting, or broken validator blocks all of them after landing; and the change spans independently owned areas (engine build files, the game project, and ChangeWorkflow scripts). Invariants: `/fp:strict` and every other compiler and linker setting reach both executables unchanged (float determinism, `Documents/FloatingPointDeterminism.txt`); client/server whole-file affinity is unchanged; no C++, shader, `.pack`, wire, or save change.

## Out of scope

- Any C++, GLSL, data, or DataPacker change; any change to a setting's value other than the steamworks directory removal and the `EngineTarget` validation; merging the three configurations' settings, deduplicating the include lists, or dropping the RenderDoc include entry.
- Making the `/compile` scripts, harness claim, bootstrap scripts, or DataPacker default project-aware (`Documents/Plans/ChangeWorkflow/ProjectAwareTooling.md`); creating the second game project.
- Moving the `ProjectConfigurations`, Globals, or `Label="Configuration"` groups out of the game projects; moving the generated `$(GameDataDirectory)\*.h` items out of them.
- Changing the `Engine|Common` include-order binding to the first discovered game; changing the resolver's output schema or roles.
- DataPacker, ThirdParty, AgentHarness, and WorktreeCli projects.

## Acceptance criteria

- Item conservation: per target and configuration, the evaluated `ClCompile`, `ClInclude`, and `None` items (full paths, plus `PrecompiledHeader` metadata on `Engine\Source\Pch.cpp`) equal the baseline sets: client 515, server 260.
- Command lines: after a `/compile` rebuild of Client and Server in Debug, Profile, and Release, the per-source compiler lines in `CL.command.1.tlog` and the linker line in `link.command.1.tlog` under each `Build\<Project>\<Configuration>\` intermediate directory match the same files from a baseline rebuild (lines sorted), except the removed steamworks `/LIBPATH`.
- Evaluated properties: per target and configuration, `DataBuildMode`, `RunDataPacker`, `GameDataDirectory`, `GeneratedDataIncludeRoot`, `OutDir`, `IntDir`, `TargetName`, `CustomBuildAfterTargets`, `EnableClangTidyCodeAnalysis`, `EnableMicrosoftCodeAnalysis`, `RunCodeAnalysis`, `CodeAnalysisRuleSet` (resolving to the existing moved ruleset), `CodeAnalysisTreatWarningsAsErrors`, `ClangTidyChecks`, and `ClangTidyToolExeAdditionalOptions` equal baseline, read through an evaluation-only `MSBuild.exe -getProperty` query with no build.
- A `/compile` PREfast Release build of the client passes, proving the moved ruleset resolves.
- A `/compile` selective `-Files` build of one `Engine/Source` `.cpp` and one game `.cpp` per target invalidates and compiles exactly those objects.
- `Test-VcxprojPair.ps1` exits 0 on both Sandbox `.vcxproj` pairs and both `.vcxitems` pairs; `Resolve-VcxprojMembership.ps1` returns `resolved` records for one Engine, one Common, one engine-shader, and one game path, and the updated worker table maps each to the right file.
- `Test-IncludeOrder.ps1 -All` returns the same result as at baseline.
- A game build without `EngineTarget`, or with another value, fails in `ValidateDataBuildProperties` with the new error.
- `Get-SessionChangeInventory.ps1` classes a changed `.vcxitems`, `.vcxitems.filters`, and `.props` path as `vcxproj`.
- No remaining route names the Sandbox VS `AGENTS.md` for an engine-wide rule: a search for that path finds only game-specific references.
- User check in Visual Studio: each `.sln` shows the engine and Common files under the shared items node in their `Engine\` and `Common\` filters, the game files under `Game\` and `DataFiles`, and builds.
