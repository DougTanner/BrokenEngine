# Move the game-agnostic cell, reset, and frame-phase plumbing from the Sandbox `Game`/`Frame` into engine `GameBase`/`FrameBase`

Line numbers cite baseline `f1d140ae26d0a8684264c8a1fa4f55c1bec1f601`. Where a statement here and the code disagree, the code wins; report the contradiction instead of matching one side to the other.

## Context

The dispatching session relayed these user directions: a second game project will be created beside `Projects/BrokenEngineSandbox`; engine code may call expected `game::` classes, globals, and members by name (`GameBase` calling `game::Game` methods is fine), but must not name Sandbox gameplay (Blaster, Spaceship, Missile, Player, `bUseMissiles`, Fleet); fleets stay game-owned; no backward compatibility; minimum sufficient change; moves keep the PostRender CRC identical.

Today the Sandbox carries engine mechanics a second project would have to copy line for line:

- Client cell management. `Game::ComputeActiveSet` (`Projects/BrokenEngineSandbox/Source/Game.cpp:145-255`) builds the client active set (confirmed cells, the client cell, the visible 3x3 ring measured against `gpCamera->mf4LargeVisibleArea`, erasing local-only cells, the at-most-9 local cells assert); `Game::UpdateActiveIslands` (`:258-272`), `Game::EnsureNextFrames` (`:276-288`), the client `FrameInputs` map fill (`:296-309`), the visible-neighbour cache (`Game.h:134-135`), and the client-cell setter and harness pin (`Game.h:137-162`) read and write only `GameBase` state. `GameBase.h:249-256` already documents the active set and client cell as `GameBase` storage, and `GameBase.cpp:421-422`, `:538`, `:915`, `:983-987`, `:1002` call these back through `game::gpGame`. The only game policy inside them is the focused-player gate (`Game.cpp:177`), the armor-drop camera shake (`:311-334`), and the harvested-transfer counter (`:342-346`).
- Session reset and frame creation. `Game::Reset` (`Game.cpp:371-403`) clears mostly engine state (tick and time, replay streams, `kSaveReplay`, `kPaused`, camera session state, smoke, particles, wind-trail history, the visual-error offset, client cell and active set). `Game::CreateNewFrame` (`:405-448`) repeats `GameBase::CreateCellAtCoordinate` (`GameBase.cpp:945-970`), and `Game::InitializeFramePostRender` (`Game.cpp:656-663`) sets the engine frame identifier and `TimeSeed` beside the game alignments.
- The visual-error offset and its three constants (`Game.h:116`, `:125-127`) are decayed by the engine (`GameBase.cpp:816-827`).
- The per-frame main-menu/game flag (`Frame/Frame.h:27-32`, `:58`) is set by the engine (`GameBase.cpp:963`) and read by the engine camera through the pure virtual `CameraBase::IsMainMenuFrame` (`Engine/Source/Graphics/CameraBase.h:190`, `Graphics/Camera.cpp:19-23`).
- The ring-tail lookup `snapshots[SnapshotIndex(iSnapshotHead, iSnapshotCount - 1)]` is repeated at `Engine/Source/Network/Client/ClientSessionRuntime.cpp:285-290`, `ReconcileReplay.cpp:340-347`, and `Game.cpp:126-131`, `:312-318`, `:453-463`.
- Frame phases. Every `Frame/Frame.cpp` phase body opens with the same `engine::ForEach*(engine::PostRenderBaseTypes {} ...)` or `InterpolateTypes` walk (`:120`, `:130`, `:205`, `:216`, `:407`, `:431`, `:442`, `:455`, `:555`, `:606`, `:619`); the game must clear the engine collision and area-damage queues by hand (`:448`, `:459`) and keep the engine Explosions render counter (`:554`, `:605`, `:617`); the version sum over engine collections lives in the game (`:26-38`); and both read paths repeat the engine collection-pair validation (`:801-803`, `:821-823`).
- `TransferRequest` with `PrepareTransferRequest`/`PushTransferRequest` (`Frame/Frame.h:80-86`, `:129-134`; `Frame.cpp:751-779`) is generic apart from its payload types.
- The `FrameInput` stream (`Frame/FrameInput.cpp:11-77`) is a generic tagged-variant list: count bound, tag check, seating the variant alternative, visit read/write, and CRC. Only the tag set, the default-alternative function, and the adopt checks are game data.
- `FlightPlanesAscend` and its three `static_assert`s (`Frame/FlightPlaneTable.h:14-31`) enforce the rule engine `FlightPlanes.h:20-21` states.
- `Game::GetStandardMenuModel` (`Game.cpp:471-489`) fills the five `StandardMenuState` bits from the engine `ClientSessionRuntime` alone.

## Design

The author recommends the shape below. Each moved body keeps its statements and their order unless a bullet says otherwise. Engine code reaches every remaining game hook by name through `game::gpGame` or `game::gpServerSession`, as `GameBase.cpp` already does. The moved members keep their names and public access, so game call sites that reach them through `gpGame->` (`ClientSession.cpp`, `FleetSelection.cpp`, `GameSaveLoad.cpp`, `AgentCommandsClient.cpp`, `ClientReconciler.cpp`, `ServerSession.cpp`) compile unchanged through inheritance.

### Stage 1 — `GameBase` session shell (no CRC, stream, or version change)

- Active set, in `GameBase`. `ComputeActiveSet()`: server, `game::gpServerSession->mpRuntime->ComputeActiveSet()`; client, the `Game.cpp:150-252` body verbatim, with the gate `ClientPlayerIdentifier().iValue != 0` replaced by a call to the new client-only game hook `bool Game::HasFocusedClientEntity() const`, which returns exactly that expression. `UpdateActiveIslands()` (client) and `EnsureNextFrames()` (server), verbatim, constructing `game::Frame`. `BuildFrameInputs()`: server, `game::gpServerSession->mpBroadcaster->BuildFrameInputs()`; client, the map fill from `Game.cpp:296-309`. `PrepareActiveSet` and `SwapFrames` call the members directly. On the client, `PrepareActiveSet` then calls the new game hook `Game::OnFrameInputsBuilt()`, which holds the camera-shake block from `Game.cpp:311-334`, at the point where that block runs today.
- Transfer harvest. `FinalizeFrameTick` calls `game::gpServerSession->mpTransferManager->HarvestTransfers()` and then the new hook `ServerSession::OnTransfersHarvested()`, which holds the `miHarvestedTransferTotal` loop from `Game.cpp:342-346`. `Game::HarvestTransfers` is deleted.
- Client cell, in `GameBase`. `mVisibleNeighbors`, `miVisibleNeighborCount`, client-only `mbClientGridCoordinatePinned`, `SetClientGridCoordinate`, and client-only `PinClientGridCoordinate` move verbatim. The `GameBase.h:249-256` comments then name `GameBase::ComputeActiveSet` and `GameBase::SetClientGridCoordinate`.
- Reset. Non-virtual `GameBase::Reset()` keeps the `Game.cpp:373-403` order, except that the game-owned statements become the new hook `Game::OnReset()`. The engine runs, in order: the log line (text `GameBase::Reset()`), tick and time, the server replay-stream and `kSaveReplay` clears, the client camera, smoke, particle, wind-trail, and visual-error resets, the `kPaused` clear, `game::gpGame->OnReset()`, the client pin clear, `SetClientGridCoordinate(kOriginCoordinate)`, and the active set reduced to the origin. `OnReset` holds the weapon-mode toggle reset, the client-player list clears, `mFleetSelection.Clear()`, and the previous-armor reset. Existing `gpGame->Reset()` callers (`Engine/Source/File/Replay.cpp:531`, `ClientSession.cpp:203`, `GameSaveLoad.cpp:70`, `:90`, `Game.cpp:528`) are unchanged.
- Frame creation. A private `GameBase` helper builds one cell's frame storage: the client ring slot or server `pCurrent` as today; `interpolate.gameFlags` from a flags argument; `postRender.uiFrameIdentifier = muiNextFrameId++` and `randomEngine.TimeSeed()` (both moved out of `InitializeFramePostRender`); then `game::gpGame->InitializeFramePostRender(rFrame)`, which keeps only the three alignment copies; then `staticData.coordinate`. `CreateCellAtCoordinate(coordinate)` calls it with `kGame`, stamps `iTick`/`fCurrentTime` from the session clock, and generates the island chain. The new public `GameBase::CreateNewFrame(flags)` clears `mCells` under `ScopedSuppressAllocationTracking`, calls the helper for the origin, generates the origin chain, and on the server creates `pNext`. It never stamps the session clock. Its callers run it before `Reset`, which then zeroes the clock, so the origin frame must keep the default `iTick` 0 and `fCurrentTime` 0 it has today. `Game::CreateNewFrame` is deleted.
- Main-menu island browser. A private game helper calls `CreateNewFrame` with the main-menu flag and then, under `if constexpr (kbDebugInput)`, rewrites the origin placements through `BuildMenuIslandPlacement` under `ScopedSuppressAllocationTracking`, so the chain is overwritten by the same single centered island as today. The client constructor (`Game.cpp:49`) and `ChangeFrame` (`:527`, always main menu per its `ASSERT`) call that helper. The other callers pass `kGame` (`Game.cpp:45`, `ClientSession.cpp:201`, `GameSaveLoad.cpp:88`) and need no override. The rationale is that both main-menu creators are game code, so no engine placement hook is needed. `GenerateIslandChain` is pure (`Engine/Source/Frame/IslandChainPlacement.cpp:227-245`), so running it first leaves the final placements unchanged.
- Visual-error offset. Client-only `mVecVisualErrorOffset` and `kfVisualErrorDecayRate`/`MaxDistance`/`MinDistance` move to `GameBase`; the decay at `GameBase.cpp:816-827` reads its own members.
- Ring tail. Client-only `engine::Cell::TailFrame()` returns the tail slot's frame, or `nullptr` when the ring is empty or the slot is null, const-correctly. `SnapshotIndex` moves above `struct Cell` so the member can stay inline. - Standard menu state. ### Stage 3 — per-frame flags into `FrameInterpolateBase` (stream order and `Frame::kiVersion` change; CRC unchanged)

- `FrameBase.h` gains `enum class FrameGameFlags : uint64_t { kMainMenu = 0x01, kGame = 0x02 }` and `FrameGameFlags_t`, the same values as `game::GameFlags`. The name keeps the `gameFlags` member name and stays distinct from the session-level `engine::GameFlags`, whose `kMainMenu` is `0x08`. Every replaced `game::GameFlags` reference must become `FrameGameFlags`, never `engine::GameFlags`: confusing the two changes the CRC.
- `gameFlags` moves to `FrameInterpolateBase`. `FrameInterpolateBase::Update` copies it from `rPreviousFrame.interpolate` before its walk; `Values()` appends it after `fDeltaTime`; `Crcs()` mixes it last, after the `ServerCollections()` loop; `LogDifferences` compares it. The game's `FrameInterpolate::Crcs` drops its `gameFlags` line, so the mix order stays base, then `gameFlags`, then `fSpawnTimer`, which is identical. `FrameInterpolate::Values()` keeps `fSpawnTimer` only, and `Update` stops copying `gameFlags`. `game::GameFlags`, `GameFlags_t`, and `using enum GameFlags` are deleted; `Game::ChangeFrame`, the engine `CreateNewFrame` and frame helper, `Frame.cpp:162`/`:414`, `Camera.cpp:30`, `PlayersRender.cpp:189`/`:216`/`:302`, `Game.cpp` (`:45`, `:49`, `:468`, `:502`), `ClientSession.cpp:201`/`:216`, and `GameSaveLoad.cpp:88` take `engine::FrameGameFlags`.
- The stream now carries `gameFlags` after the base values instead of after `fSpawnTimer`. Increment the `Frame::kiVersion` base literal by one (134 at baseline), so older saves, replays, and peers are rejected (Hello gate: `Engine/Source/Network/Server/Server.cpp:600`). `FrameInput::kiVersion` and `engine::kiProtocolVersion` are unchanged: no `StatusChange`, `TransferData`, or packet layout changes.
- `CameraBase::IsMainMenuFrame` stops being virtual: a private member reads `rFrameInterpolate.gameFlags & FrameGameFlags::kMainMenu`. `Camera::IsMainMenuFrame` is deleted.

### Stages

Stages 1 and 2 leave every CRC input, stream byte, and version value unchanged, so a replay recorded by the baseline build still loads after Stage 2, which proves the CRC is unchanged across the builds. Stage 3 is last because its version bump ends that proof.

## Risk triggers and invariants

Change Workflow Tier 3. The highest triggers are the save/replay serialization and data-layout change in Stage 3 (stream order, `Frame::kiVersion`) and code moves inside the deterministic CRC path (`RunFrameTick` phase dispatch, `Crcs`); the change also spans independently owned subsystems (engine `GameBase`, Frame, client Network, Graphics camera, and the game).

- Bit determinism and CRC (`Documents/FloatingPointDeterminism.txt`): every phase keeps its walk order (engine types, explicit Players, game tuple); the queue clears stay after the last consumer of each phase; the CRC mix order is unchanged; nothing moved reads `gpGame`, wall time, or render state inside a tick; `TimeSeed` and frame-identifier assignment keep their per-frame order.
- Serialization: Stages 1 and 2 change no stream byte and no version value. Stage 3 bumps only `Frame::kiVersion`; there is no compatibility path.
- Trust boundaries: replay `FrameInput` reads keep the count bound, unknown-tag rejection, the alternative seated before the payload read, and both adopt rejections with unchanged messages; `AdmitSpawnTimer` stays on `FrameInterpolate::Read`.
- Allocation: no new main-loop allocation; each moved body keeps its `ScopedSuppressAllocationTracking` scope, and the menu placement rewrite runs under one.
- Threading: the queue clears run on the per-coord dispatch thread inside `RunFrameTick`, where those `thread_local` queues live.
- Affinity: client-only and server-only members keep their `BT_CLIENT`/`BT_SERVER` guards; no file is added, removed, or moved.
- Engine/game contract (`Engine/Source/AGENTS.md` `## Hub Conventions`): no engine member, signature, or template names a Sandbox gameplay concept. The game hooks the engine calls by name are `InitializeFramePostRender`, `OnReset`, `HasFocusedClientEntity`, `OnFrameInputsBuilt`, and `ServerSession::OnTransfersHarvested`. No game header joins an aggregated engine header.
